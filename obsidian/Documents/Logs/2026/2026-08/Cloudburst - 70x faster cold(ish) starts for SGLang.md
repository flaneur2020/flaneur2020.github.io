- 作者要跑一个 122B 的 MoE 模型在 B200 的 k8s 上；
- Cold Start 的时间分布：![[Screenshot 2026-08-08 at 21.37.11.png]]
	- 可见有 531s 都是 weight loading 的时间；
	- 对 sglang 来说，跑推理块 10% 比优化 10s 的启动速度更有优先级；
- 对于 sglang 能够缓存的内容，利用起来，就可以实现热启动：![[Screenshot 2026-08-08 at 21.39.58.png]]
	- kernel cache 缓解了大量的编译时间，page cache 处理了其余部分；
	- 权重仍然在磁盘上，但读取了一次之后，就会在 page cache 里面而不需要回磁盘；
	- 不过 88s 里面只有 31s 是真正加载权重么，其他时间是 import、配置解析、auto-tune、预热等等。
	- 权重传输的带宽来估算，下限介于从磁盘的 15s 和从内存加载的 1.8s 之间；
- 想做的事情是，让 sglang 把启动时候做的所有事情都缓存起来，打包成一个易于恢复的完整的包；
	- linux 上主流的办法就是 CRIU，用 nvidia 的 cuda-checkpoint 插件来捕获、恢复 GPU 设备状态；
	- 但是对 sglang 做朴素的 criu checkpoint 会包含所有 GPU 内存，在 B200 上就是 192GiB；
	- 其中大部分都是权重和 kv cache，而 sglang 已经知道如何重新加载这些内容；
	- 作者将它们剥离出来，checkpoint 从 192GiB 缩小为了 6.6GiB，代价是唤醒时需要重新加载权重；![[Screenshot 2026-08-08 at 21.47.44.png]]
- 作者的设备上有大量的内存，所以最好的情况就是达到 PCIe 带宽；这台机器的配置是 64GiB/s；
	- 首先是重新加载权重，这已经将它从热启动时候的 31s 降到了恢复时候的 19s；不再从磁盘读取 safetensor，而是利用 checkpoint 存储实际的内存分配的序列化表示；
	- 磁盘的上限很低，作者想要的是内存的上限，1.8s；作者的做法是在恢复开始之前，就将权重预热到内存中；
	- 会弄一个 daemon 进程，它会监控检查点目录，将内容暂存到内存中，然后通过 socket 向 torch 进程传递文件描述符来传递内存；
	- 从 cpu 拷贝到 gpu 的过程，需要开启大页来加速传输；
	- 搞这一波之后，可以到 9.6s： ![[Screenshot 2026-08-08 at 21.53.31.png]]

大致上的思路：

- DHT 的节点只用来保存 `内容哈希` 到 `peers` 的映射关系，注意这里的 peers 是内容提供者的地址，并非 DHT 的节点；
- DHT 大概只有两个操作：
	- `annonce_peer(content_hash, peer_addr)`：宣称一个内容哈希，存在于一个 `peer_addr` 上；
	- `get_peers(content_hash)`：根据内容哈希，找到 peer_addr 的列表；
- DHT 中每个节点有一个 Node ID，这个 Node ID 有 160 位，和内容哈希的长度相等；
- 每个内容哈希可以和 Node ID 通过 XOR 计算距离，如果完全相等，就是距离为零，理论上这个内容就该存储在这个 Node 上；
- annonce 内容时，就去寻找 DHT 中，距离这个内容哈希最近的几个 DHT 节点（8 个？），都登记进去，增加冗余性；
- 对应的，寻找内容的 peers 时，也在 DHT 中寻找这个内容哈希最近的几个 DHT 节点，从这几个节点中问到一个就行，就能拿到 peers 列表；具体的实现时，热门的资源可能会随机分散在几个不同的 DHT node 上；
- 怎么让我们能够找到一个内容，对应的最近的 DHT 节点列表？
	- 大概的思路是，每个节点要保存下来一组邻居信息；
	- 这里一个编码格式和分桶的策略，大约是，DHT Node 内，距离越近，就精度越高，距离越远，则精度越少；
	- 每个桶同样都是 8 个，但是桶号越大，它的距离是越是指数级增长的，这就意味着桶号越小，就越准；（见后面的例子）
	- 寻找的时候，我们随便连几个 DHT Node，可以顺着它们远距离的 Node，找到近距离的 Node，在这些近距离的 Node 中，找到更近的 Node，继而找到最近的几个 Node；
- DHT 似乎并不保证一定找的到 DHT 里存在的内容，但是实际上工作情况很好，找到 peers 列表的概率很高，冗余的存在让节点的下线变得可以容忍；每个 announce 的内容都有一个 ttl，节点需要定期注册自己回来，和服务注册类似；

简化一下 160 位的情况，设 ID 的长度为 8 位，这个分桶的思想有点像 Radix tree，不过这颗树上不是绝对的地址，而是和我们的 Node ID 计算 XOR 的距离：

| 桶   | 存放的节点前缀     | 距离范围      |
| --- | ----------- | --------- |
| 桶 0 | `1xxx xxxx` | 128 ~ 255 |
| 桶 1 | `01xx xxxx` | 64 ~ 127  |
| 桶 2 | `001x xxxx` | 32 ~ 63   |
| 桶 3 | `0001 xxxx` | 16 ~ 31   |
| ... | ...         | ...       |
| 桶 7 | `0000 0001` | 1         |
